# wiki-to-slides.md — NPB Wiki 文章轉互動式網頁簡報規範（定稿候選 v0.4）

> 適用：**已有完整賽後分析文章**，希望建立或更新簡報。這是一份內容轉換規範，不是重新蒐集比賽資料或重新評級的授權。

## 1. 轉換目標與禁止事項

目標是讓未觀看完整比賽的讀者，也能看懂比賽過程、各球員重要表現、表面數據的限制，以及分析結論背後的理由。簡報應比 Wiki 容易瀏覽，但不能變成只有比分與明星球員的摘要。

**禁止：**自行新增未經原文支持的球路、球速、球種、擊球位置、教練暗號、球員心理、失誤責任細節、傷勢因果、錯判或戰術意圖；不得因簡報版面重評球員或擅改原始等級。不要從網路補圖片，也不使用 AI 生成的球員照片。

## 2. 來源與內容對應

- 每份簡報只能綁定到一個明確的 `game-id` 與其 Wiki 來源文章；跨場比較另需明確任務與來源。
- 匯入來源快照（若具備公開及保存許可）與已整理 Wiki 文章分開保存，並維護 `wiki/index.md`；不得將來源快照當成已確認的簡報內容稿。
- 如純文字轉存導致原先的圖片、圖表或超連結消失，記錄原始資料缺漏，不自行發明 URL、圖表數據或具體畫面。
- 原始 Wiki 檔案為分析結論的權威版本。簡報可改寫敘述的形式，但**不得改變確定性、條件、原因歸屬與原始評價**。
- 區分：A. 事實／官方紀錄；B. 當事人說法；C. 媒體評論；D. 分析推論。無法區分時在內容稿標記待確認。
- 不因內容是「已完成文章」就自動宣稱已重新核對官方資料。來源只有網站名稱、沒有網址時，清楚標為「原文章列出來源名稱，連結待補」。
- 所有量化圖表須可回推來源中的實際值；沒有分母或原始數據不得繪製看似精確的進階統計圖。

## 3. 轉換前盤點

1. 取得完整 Wiki 文章，確認日期、賽事性質、對戰、比分、場地、局數與來源資訊。
2. 產生兩隊「實際出賽名單」並整理為 `slides.json` 的 `roster` 標準清冊，包含每位球員的唯一 `player_id`、球隊、姓名／語言、角色、綜合與單項評級、評價限制及來源 ID；一人兼任不同角色仍只建一筆。
3. 記下所有**多面向評級**（例如「打擊 A-；綜合 C」），不得只留下其中一項。
4. 建立比分／事件時序表，核對順序、局數及先後因果；特別檢查換投、跑壘出局、守備失誤的描述。
5. 盤點值得獨立呈現的「關鍵打席」「守備／跑壘」「投手救援」「教練與裁判」「季後賽情境適性」。
6. 若素材有圖片消失、來源網址遺失、原文含不明圖表殘留等情況，列為轉換限制，不自行重建無依據的圖像。

### 3.1 出賽球員完整性核對表

至少包含：`player_id｜球隊｜原始姓名及 name_lang｜角色（可複數）｜原始綜合評級｜其他面向評級（若有）｜Wiki source-id｜roster-overview 頁 ID｜是否有深入分析頁`。

- 此清冊與 `slides.json.roster` 必須完全對應；單一球員即使兼任代打、代跑或守備仍只列一次，角色記在 `roles` 陣列。不得根據國籍自行改寫姓名或推定字形語言。
- 全部 `roster-overview` 投影片的 `roster_player_ids` 聯集必須與 `roster.player_id` 集合相等，並且總覽不重複；深入分析頁可重複出現球員。原始資料有缺漏時先記錄並回報，不可捏造評級以湊齊。

**案例驗證**：目前選定的 2026-10-14 日本火腿對軟銀測試文章，文章清單包含兩隊合計 **34 名實際出賽者**（日本火腿 17、軟銀 17）。這個數字只適用於該測試案例，絕不可寫成所有 NPB 比賽固定人數。

### 3.2 來源定位與日文姓名

- Wiki 的重要章節、球員或關鍵事件使用穩定來源標記，如 `<!-- source-id: 4th-inning-turnaround -->`。`slides-content` 和 `slides.json` 的 `source_sections` **均只填實際存在的來源 ID**；標記不隨文章行數或標題順序改變。規則詳 `AGENTS.md` 第 3.3 節。
- 新增來源標記只屬格式整理，不得改變分析文字；既有文章需依總規則取得核准，若標記未建立，來源驗收必須標示未通過／待處理。
- 日本球員姓名**不必然是日文顯示字串**；原始姓名若為中文寫法，用 `name_lang: zh-TW`。確有日文寫法時才用 `ja`，英文原名用 `en`；日文保留漢字、平假名、片假名、異體字與日文標點，套用 `UD Digi Kyokasho`；混合語言時以 `name_segments` 明確切分。禁止從國籍或漢字 Unicode 範圍推定日文字形。
- 英文、數字與拉丁標點遵照 `design-system.md` 使用 Times New Roman；不要對原始姓名執行改字、假名漢字化或不必要的正規化。

## 4. 簡報內容深度與彈性頁數

- 採**平衡型**：完整球員總覽＋關鍵個案深入分析；頁數由內容決定，不設硬性上限或每場固定 27 頁。
- 一般場次約 15–25 頁可作規劃參考；測試文章屬季後賽且事件複雜，初估約 27 頁，仍可隨內容調整。
- 先確定每頁要回答什麼問題，再選擇版型；不得僅按 Wiki 原段落逐頁拆開。
- 頁面超載時優先**拆成多頁**；不得透過刪除球員、壓縮重要分析、縮至難讀的字級解決。手機窄螢幕或 `200%` 縮放下也不得裁切，依 `design-system.md` 允許合理改排／捲動。
- 重複的不佳打席可濃縮為模式分析，但重要的優秀打席、不同策略及實際攻擊成果應儘量區別呈現。

## 5. 標準敘事章節（可增減頁數）

| 順序 | 章節 | 建議視覺形式 | 必要資訊 |
|---|---|---|---|
| 1 | 賽事封面與概覽 | 封面／比分板／數據卡 | 日期、雙方、比分、賽事類型、重要基本數據 |
| 2 | 全員快速總覽 | 多頁球員評級清單 | **兩隊所有實際出賽球員**、評級、簡短貢獻與限制 |
| 3 | 比賽流程 | 各局得分圖／時間軸 | 關鍵轉折、雙方攻勢、換投與重要事件 |
| 4 | 關鍵攻防 | 事件分析卡／對照頁 | 事件、證據、結果及不可過度推論的部分 |
| 5 | A 隊表現 | 球員卡／投手卡／守備對照 | 打擊優先，兼顧投球、守備跑壘及替補 |
| 6 | B 隊表現 | 與 A 隊相同原則 | 不因勝敗而改變衡量標準 |
| 7 | 特殊因素（視需要） | 裁判／戰術／季後賽情境頁 | 僅列有可靠證據且具實質意義的內容 |
| 8 | 全場總結與來源 | 結論卡／限制說明 | 最值得注意球員、易誤判表現、後續觀察、資料來源 |

章節中的「A 隊、B 隊」只是角色位置；頁面應用真實球隊名稱，且兩隊使用對稱的分析原則。

### 5.1 八種允許的 JSON `layout`

此清單與 `AGENTS.md` 第 3.2 節相同，所有簡報都只能使用這八種：

`match-overview`、`roster-overview`、`game-timeline`、`key-play`、`player-analysis`、`comparison`、`summary`、`sources`。

- 全員總覽使用 `roster-overview` 並填 `roster_player_ids`；正文的單一球員分析使用 `player-analysis`。
- 重要打席或守備事件用 `key-play`；依局數排序的比賽轉折用 `game-timeline`；不同面向評級對照用 `comparison`。
- 不要創造 `event-timeline`、`player-card` 等同義版型識別碼。若確實有新需求，先核准變更規則與共用渲染器。

## 6. 重要內容如何轉成視覺版型

| 輸入內容 | 優先使用的版型 | 風險控制 |
|---|---|---|
| 比賽比分與各局得分 | 比數卡、各局條列／折線圖 | 值與方向正確、標明先攻與後攻 |
| 重大得分轉折 | 事件時間軸、累積比分／分差圖 | 事件順序依 Wiki、不得創造未記載事件 |
| 球員快速總覽 | 全員清單＋**正圓形 S～E 徽章** | 保留所有出賽者與評級，不因空間刪人 |
| 關鍵打者 | 成績／情境／分析結論卡 | 不將「結果」直接當成「能力」 |
| 多面向評級 | 左右並排雙欄 | 標示例如「打擊 A-」與「綜合 C」 |
| 投手表現 | 局數／用球／責失／危機分析 | 不能把失分、自責分與繼承跑者混同 |
| 守備／跑壘事件 | 事件分解卡／事實—分析對照 | 不自行重建球場位置、動作、失誤難度 |
| 裁判與戰術 | 證據標籤／分析說明 | 無充分證據時僅述限制 |
| 季後賽情境適性 | 正反證據與樣本限制 | **只用文字，不轉換成另一套字母評級** |

禁止使用真實照片、球團隊徽或網路影像。使用自行編排的 CSS、HTML、SVG 圖表；圖表必須有資料來源及可理解的標題／標示。裝飾性圖形不能暗示不存在的數據或事件。

## 7. 逐頁內容稿資料格式

每張投影片都要有：頁碼（或暫定序號）、章節、**唯一核心論點**、該頁精簡內容、選用版型、來源對應、事實／推論標示、必要的圖表資料、遺留限制。

可使用以下 Markdown 模板（僅為格式示例，非新增一場賽事）：

```md
## Slide 12 — 四局下的逆轉過程
- section: game-turning-points
- layout: game-timeline
- message: 四局下多項攻守事件共同造成逆轉，不能單歸因於一次失誤。
- facts:
  - 比分由日本火腿領先 3：1，轉為軟銀領先 6：3。
  - 其他事件請依 Wiki 原文順序逐項填寫。
- interpretation: 依原文清楚分開投手控管、守備執行與軟銀進攻成果。
- chart-data-source: wiki/2026/<game-id>.md；只使用核對過的實際數值
- source-sections: [game-flow, 4th-inning-turnaround]  # 對應 Wiki 中實際存在的 source-id
- caveats: 不補造失誤動作細節或球路。
```

禁止將此模板當成比賽真實紀錄的唯一證據。轉入 `slides.json` 時，應保留對應來源及限制資訊，避免網頁渲染時將推論誤當事實。

### 7.1 逐頁內容稿與 JSON 區塊對應

- 每頁的 `layout` 必須採第 5.1 節白名單值；`source-sections` 使用穩定來源 ID，而不是行數、自由輸入的標題或不存在的網址。
- 整理球員名單時先建立全場 `roster`，並為每人指定發布後穩定的 `player_id`。內容稿的總覽頁列出 `roster-player-ids`，產生 JSON 時成為 `roster_player_ids`。
- 每頁明確指定 `title_segments`，包含已核對球員姓氏、全名及英文姓名，所有片段串接必須與原始標題完全相同。依資料類型填寫 `text`、`stat`、`player`、`event`、`chart`、`table` 區塊，必填欄位、資料型態與語言標記採 `AGENTS.md` 第 3.4、3.5 節；**不可只用自由文字來跳過區塊資料契約**。
- `text` 區塊標記證據類型；`stat` 保留原始值與單位；`player` 使用 `player_id` 回查清冊；`event` 正確標示半局與事件順序；`chart` 填實際座標數值及出處；`table` 逐欄填入來源表格內容，保留未進攻的 `X` 與合計，不可將 `X` 換成 0。
- 頁面的 `source_sections` 為該頁所有內容區塊來源 ID 的聯集；每個承載分析或事實的區塊須有自身非空 `source_sections`。限定語氣和資料不足說明放在 `caveats`，但不可藉此刪除原文章的核心論述。

## 8. Wiki、內容稿、簡報檔案的一致性

同場須共用同一 `game-id`：

```text
wiki/YYYY/<game-id>.md
slides-content/<game-id>.md
docs/slides/<game-id>/index.html
docs/slides/<game-id>/slides.json
docs/data/games.json   # 收錄該場目錄項目
```

- `games.json` 必須符合 `AGENTS.md` 第 3.1 節的 `schema_version`、欄位名稱與型態；其資訊以首頁基本資料、簡報相對路徑及專案追溯路徑為限，避免重複儲存詳細球員分析。
- `slides.json` 需符合 `AGENTS.md` 第 3.1～3.5 節的 `roster`、`slides`、`layout`、`roster_player_ids`、`blocks`、`source_sections` 與 `caveats` 契約，並與內容稿逐頁對應；前端以共用版型呈現，不得自行增加沒有規則依據的版型或修改欄位名稱。
- Wiki 原始檔案名稱或內容若有重大更動，必須追蹤受影響的簡報、`wiki/index.md` 與 `games.json`，並經使用者同意才更新。
- `wiki/index.md` 是 GitHub 上的全文索引，`games.json` 是公開網站上的簡報索引；兩者用途不同，但日期、對戰、`game-id` 不得不一致。
- 用於 GitHub Pages 的 URL 必須正確處理子目錄、大小寫及相對路徑；不得假設網站一定部署在域名根目錄。

## 9. 內容驗收清單（必須逐項回答通過／未通過／未測試）

1. 比賽日期、球場、對戰、比分、局數及官方基本資訊與 Wiki 一致。
2. 所有實際出賽球員均在 `roster` 中，且所有 `roster-overview` 頁的 `roster_player_ids` 恰好涵蓋清冊一次；姓名與角色未遺漏，保留日文原字形、假名及語言標記。
3. 所有 S～E 評級與 Wiki 一致；複合評級不混為單一分數。
4. 比賽轉折、攻守責任、投手調度及裁判因素未被扭曲。
5. 沒有把無證據的臆測、相關性或媒體評價寫成確定因果。
6. 文字確實經過資訊整理，而不是原文大段貼入投影片。
7. 圖表有可檢核的實際數據，沒有為美觀杜撰球路或照片。
8. 各頁與各內容區塊可透過 `source_sections` 追溯至 Wiki 中真實存在的穩定 `source-id`；不存在虛構來源網址。
9. 所有內容都以 `design-system.md` 視覺規範渲染，沒有字型錯配、文字溢出；確認八種共用版型一致，並在 Windows Chrome、手機窄螢幕、`200%` 縮放、鍵盤焦點及灰階等情況下按實際測試結果記錄。
10. `wiki/index.md` 與 `games.json` 的同場索引一致；六種 `blocks` 的欄位、`event` 順序及 `chart` 數據形狀符合契約；翻頁、上一頁／下一頁與返回首頁功能正確。
11. 網站實作後應執行 `AGENTS.md` 第 9.1 節規劃的自動檢查、9.2 節的本機預覽；**腳本未建立或未執行時只能標示未測試**。

驗收失敗時先定位為**來源缺漏、內容抽取、轉換、呈現、程式**哪一層，避免為了讓頁面看起來正常而偷偷改動 Wiki 原文。
